# OH MY BABY — Access Control Model

## قاعدة النظام

الـOwner هو جذر الصلاحيات. كل حساب آخر يملك فقط ما تم منحه له صراحةً.

النظام يقسم الوصول إلى طبقتين:

1. **Permissions** — ماذا يستطيع الحساب أن يفعل؟
   - مشاهدة
   - إنشاء
   - تعديل
   - أرشفة/حذف حسب الوظيفة
   - قبول/رفض/تعيين/تحويل...

2. **Data Scope** — على أي بيانات يستطيع تنفيذ هذه الصلاحية؟
   - `all`: كل بيانات القسم.
   - `section`: قسم/أقسام محددة مثل `decor`.
   - `assigned`: البيانات المسندة للحساب فقط.
   - `related`: البيانات المرتبطة بالسجلات التي يستطيع الحساب رؤيتها فقط.

## سقف التفويض Delegation Ceiling

إذا أعطى الـOwner Admin صلاحية إنشاء حسابات أخرى:

- الـAdmin لا يستطيع منح Permission لا يملكها هو.
- الـAdmin لا يستطيع منح Data Scope أوسع من نطاقه.
- الـBackend يفرض هذه القاعدة حتى لو تم تزوير الطلب من المتصفح.
- الحساب الأقوى لا يمكن إدارته من حساب أدنى منه.

مثال:

- Admin A يملك `orders.view` فقط ونطاقه `decor`.
- يستطيع إنشاء Admin B بـ `orders.view` ونطاق `decor` أو أضيق.
- لا يستطيع إعطاء B `finance.view`.
- لا يستطيع جعل B يرى كل الطلبات.

## Admin التزيين

يمكن إنشاء Admin وإعطاؤه:

- صلاحيات المنتجات/الطلبات المطلوبة فقط.
- Data Scope من نوع `section` واختيار `decor`.

عندها APIs الخاصة بالمنتجات والطلبات تطبق النطاق من السيرفر، وليس فقط من الواجهة.

## Delivery

الافتراضي لحساب Delivery:

- الطلبات: `assigned`
- بيانات الزبائن: `related`

وهذا يمنع السائق من رؤية طلبات سائق آخر إلا إذا قام الـOwner صراحةً بتوسيع نطاقه.

## التوافق مع الحسابات القديمة

إذا كان حساب قديم لا يحتوي `data_scopes`، يتم تطبيق Default آمن متوافق مع دوره حتى لا تتعطل الحسابات بعد الـmigration.

## نقاط الحماية الحالية

- Permission checks على الـBackend.
- Data Scope filters على الطلبات والمنتجات ولوحة الإحصائيات والتوصيل.
- منع تنفيذ Action على Order خارج نطاق الحساب.
- منع تعديل Product خارج نطاق الحساب.
- Audit log لإدارة الحسابات.
- Primary Admin لا يحصل على صلاحيات مخفية؛ الـOwner يحدد صلاحياته مثل أي Admin.
